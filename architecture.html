LD-Watch - Interactive Architecture and Decision Guide

Real-time dynamic linker telemetry and threat detection project. This page is optimized for explanation in review meetings and viva presentations.

Domain: Linux Security Core Interface: LD_AUDIT Languages: C + Go Storage: SQLite (planned)
Reality check: README describes full pipeline, but current implementation is mainly the C audit hook prototype. Collector/engine/CLI are still mostly pending.

Architecture View

Current runtime flow: Program -> ld.so -> audit.so hooks -> stderr logging Not yet wired: - audit.so -> Unix socket sender (ipc.c TODO) - collector socket server and struct parser - detection rules execution engine - SQLite event + alert persistence - operational CLI commands

Core Engineering Decisions

DecisionReason
Use LD_AUDITObserves loader behavior exactly where linker attacks occur.
C for hooksRequired by glibc audit ABI and low-level runtime integration.
No printf in hot pathwrite() reduces re-entrancy/allocation side effects in audited process.
Cookie map for SO provenanceNeeded to resolve symbol source/target in la_symbind64 events.
Go for backend toolsCleaner concurrency and faster development for collector + CLI.
SQLitePortable, demo-friendly, no external DB dependency.

Overall completion estimate

Already Done

  • Audit library build pipeline and Makefile integration
  • LD_AUDIT hooks for SO load/search/symbol bind
  • Critical-symbol-focused logging strategy
  • CI workflow scaffold and Linux dependencies install

Must Do Next

  • Define and finalize binary IPC event struct
  • Implement collector receiver and parser
  • Persist events and build first alert rule
  • Connect one CLI command end-to-end

Caveats

  • Static binaries are outside LD_AUDIT coverage.
  • setuid execution can sanitize LD_* environment behavior.
  • Current visibility is log-based, not persisted telemetry.
  • MAX_OBJECTS is fixed and needs overflow strategy.
